## Local verification

Use the project’s dedicated Python environment. Semgrep has a separate environment because its dependency constraints conflict with the other tools.

```sh
npm ci
npm ci --prefix backend
python3.12 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r backend/requirements.lock
.venv/bin/python -m pip install -r backend/requirements-dev.txt
.venv/bin/python scripts/setup-security.py
npm run hooks:install
npm run security
```

`output/security/gate.json` identifies the source hash actually scanned and records success/failure. `output/security/` contains redacted findings, test output, package provenance and the three SBOMs. A successful local gate is not a production certification, live IdP test, GitHub CI run or deployment approval.

No external account credentials are needed for local tests; they create real RSA-signed test tokens and stub only the JWKS transport. Negative tests verify expired/wrong-audience/forged/no-MFA tokens, cross-user access, reader writes, malicious origins, large bodies, quota exhaustion, changed audit rows, failed/missing PR controls, planted secrets and unsafe JavaScript.

## Required activation before a new production release

1. Choose hosting, region and IdP. Configure exact issuer/audience/JWKS and MFA plus role claims. Do not enable `SCAMSHIELD_DEV_AUTH` outside loopback development.
2. Provision a persistent random audit signing secret (at least 32 characters) and model credentials in the host vault. Do not reset the audit key each startup.
3. Apply the new D1 migrations once before running the updated Site. Preserve existing data; explicitly migrate verified owners. Do not expose the Worker directly, because it trusts Sites dispatcher identity headers.
4. Connect your GitHub repository. Require `security-gate`, an independent human approval, stale-review dismissal, no direct main pushes, admin enforcement, and production-environment approval restricted to main. Supply a read-only policy token to the release verifier.
5. Complete the container image scan/build, vault/edge configuration, backup scheduler, off-host checkpoints and monitoring. Run the actual sign-in/MFA, two-user access and restore drills in staging.
6. Run the reviewed release workflow. Verify signed artifacts with `gh attestation verify` for the expected repository before adding your cloud-specific deploy step. Keep the original owner-private audience until explicitly changed.

References used for integration contracts: [PyJWT verification API](https://pyjwt.readthedocs.io/en/latest/api.html), [Cloudflare D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/), [GitHub artifact attestation action](https://github.com/actions/attest), [Gitleaks releases](https://github.com/gitleaks/gitleaks/releases).

## Stateless judge demo

`SCAMSHIELD_PUBLIC_DEMO=1` is an explicit deployment mode that exposes only `/analyze` plus the built frontend. It accepts up to 4,000 text characters and stores no case or community report. Saved-case and operations routes remain protected by OIDC/MFA/RBAC. Local browser OCR can supply reviewed text; direct screenshot uploads are rejected in this mode.

SQLite persists peer/global quotas and audit metadata. The public analysis budget is 6 requests per peer per minute, 20 global per minute and 200 global per day, with existing write quotas also enforced. An edge WAF, TLS and a stable audit secret are still deployment requirements. The supplied Render Blueprint requires persistent storage and therefore uses a paid Starter plan; it must not be applied without a hosting budget decision. A free-tier Gemini key does not make hosting free.
